## Token-efficiency improvements
- **BFS query cache in SQLite.** Cache results of expensive multi-hop traversals (`find_references`/`find_calls`/`find_callers`/`impact_analysis` with `depth` > 1) keyed by `(symbol_id, tool, depth, offset)`, invalidated whenever `reindex` runs. Avoids recomputing the same graph walk if an agent repeats a similar query within a session. **Touches the SQLite schema** (new cache table) — per `CLAUDE.md`'s cross-cutting rule, this needs an issue opened first, not a drive-by PR.
- **Agent-maintained Obsidian session note.** At the close of a task, the agent appends a short note (decisions made, why, what's left) to a per-session or per-topic page in this vault, so the next session starts by reading one note instead of reconstructing context from `git log`/conversation history. Doesn't touch `crates/` or the MCP tool surface — pure docs workflow, no cross-cutting constraint.

## Resolution precision (after the Rust prelude fix)
Each item has failing labels in `crates/mct-eval/suite-resolution.json` (none of the 29 labels resolves to the wrong place). A fix must turn its labels from wrong to correct or ambiguous without raising the wrong count of any suite.
- [x] **D2. Builtins resolved into test fixtures:** Python builtins and ECMAScript globals are `external` in the parsers when nothing in the file binds them (`symbol-coverage.md`). On this repository's index, 121 such relations that pointed at corpus fixtures (`Loan.open`, `Page.map`, `Money.max`, `round`) became `external`.
- [ ] **D2b. Production code resolved into fixtures by any other name:** a general "no production → fixture edges" rule changes the `relation_candidates` view, so it needs an issue first. No label fails today; add one before the fix.
- [~] **D3. Calls resolved to non-callable kinds:** done for Java: a method invocation carries the target kind `method`, which the existing `target_kind` filter applies, so no migration was needed. The `total()` label is now unresolved instead of resolved to the field `Ledger.total`. Record components are indexed as their implicit accessor methods, so `p.amount()` on a record is not resolved to another class's `amount()` by name. On this repository's index, 12 wrong Java call targets (fields, or a same-named method of another class) became ambiguous or unresolved; 13 calls became resolved, 11 correctly and 2 wrongly (`currency.name()` is the JDK's `Enum.name()`, which needs D5/D9). C# and Kotlin are not changed: a delegate field or a function-typed property can be invoked there. A general per-language callable-kinds rule still changes the `relation_candidates` view and needs an issue first. Rust tuple variants are indexed as `constant` and must still resolve.
- [~] **D6. Imports resolved by name:** done for Python and JS/TS: a call to an imported name carries the imported module as evidence, and a third-party import never resolves into the repo. Both D6 labels in `suite-resolution.json` are now correct. On this repository's index, for the call names any file imports: Python, 39 ambiguous calls became resolved (all `search` imported `from core`, each checked), 6 wrongly resolved calls (`math.log`, `tarfile.open`, `shlex.quote`, Django `render`) and 48 ambiguous stdlib calls became unresolved. JS/TS, 1818 ambiguous calls became resolved, each to the file its import names (`./core.js`, `./i18n.js`, `./harness.mjs`); 46 resolved and 12 ambiguous calls became unresolved, all to package imports (`vitest`, `@testing-library/react`, `graphology`, `fumadocs-ui`), each wrong or unprovable before. Rust already does this for `use`; Go, Java/Kotlin single-type imports and the other languages are pending.
- [~] **D5. Receiver types:** done for Java: a call's receiver is qualified by its declared type, and an unproven receiver is a member call (ambiguous, never resolved by a unique name). On this repository's index, Java resolved calls went from 181 to 215; each of the 95 new or changed targets is the receiver's declared type, and the 2 `currency.name()` calls are no longer wrong. 57 calls lost their resolution, mostly JDK calls that had been resolved by name into the repo; 4 were right before (2 inherited `getById`, 2 on a call result). Inherited methods need supertype data (issue #321). Done for JS/TS: a call's receiver is qualified by its TS-declared type (annotation, `new T()`, class field, parameter property; `this.m()` when the class declares `m`), and a local of unproven type or any other expression is a member call. The TS D5 label is now correct. On this repository's index, for every name called as `x.m()` in a JS/TS file (940 names): 446 resolved calls became ambiguous and 327 became unresolved. 534 of them are inside the minified bundles (`*-dist/*.js`), where a unique name inside the bundle proved nothing. Outside them, almost all were platform methods resolved into the repo by name (`path.split()` → `Money.split`, `el.getAttribute()` → the graphology bundle, `menu.contains()` → `MoneyRange.contains`, `location.hash.replace()` → a test harness). 4 that became ambiguous were plausibly right (`o.isLarge()`, `session.skip()`, `client.orders()`, `cache.invalidate()`), and 7 right ones became unresolved (`core.hrefTo()` on a loaded module, `bridge.ago()`), because a member call only reaches a method. 5 ambiguous calls became resolved, each to its receiver's declared type. Host globals (`console`, `document`, `window`) are not ECMAScript globals, so `console.log` still resolves to a fixture's `log` (D9). Done for Kotlin, with the same rules (a parameter or `val x: T`, `= T(…)`, a class or constructor property, a capitalized object name, `this.m()` when the class declares `m`). On this repository's index, for every name called as `x.m()` in a Kotlin file (152 names): 12 ambiguous calls became resolved, each to the receiver's declared type (`service.place()` → `OrderService.place`, `invoice.describe()` in the billing fixture → that fixture's `Invoice`). 7 resolved calls became unresolved, all wrong before (`text.trim()` → a fixture's `Strings.trim`, `weights.sum()` on `Int` → an extension on `Iterable<Money>`, `currency.hashCode()` → `Money.hashCode`). 16 resolved calls became ambiguous: 4 were wrong (`cache.clear()` and `pending.clear()` on a map and a list, `shares.sum()` on `Int`, a `BigDecimal.hashCode()`); 12 were right and are now unproven: 6 `sum(currency)` extension calls on a mapped list, 3 `convert()` through a property chain, and calls on `it`, a call result and `this@Money`. 2 ambiguous JDK calls (`BigDecimal.compareTo`, `toString`) became unresolved. Done for C#, with the same rules (a parameter, a typed local, `var x = new T()`, a `foreach`/pattern/`out` variable, a field, a property, a primary constructor parameter, a capitalized type name, `this.M()` when the type declares `M`). On this repository's index, for every name called as `x.M()` in a C# file (148 names): 25 ambiguous calls became resolved, each to the receiver's declared type (`_notifier.Notify()` ×7 → `INotifier.Notify`, `options.Get()` ×3 → `Options.Get`, `SystemClock.Create()`). 17 resolved calls became unresolved: 9 were wrong before (`value.Trim()` on a `string` ×3 → a fixture's `Strings.Trim`, `int.TryParse()` ×3, `_lock.Dispose()` on a `ReaderWriterLockSlim`, `_lines.Remove()` on a `List`, `Id.GetHashCode()`); 8 were right and are lost: 7 methods inherited from `InMemoryRepository` (`_products.GetAsync()` ×4, `Products.Dispose()` ×3) and 1 extension method (`Amount.InRange()`). 29 resolved calls became ambiguous: 4 were wrong (`EqualityComparer<T>.Default.Equals()` → `Entity.Equals`, a tuple's and a `decimal`'s `CompareTo()` → `Location.CompareTo`, `tag.Trim()`); 25 were right and are now unproven: calls on a call result or a property chain (`Host.OrdersService.DraftAsync()`, `source.Reserve()` on `var source = Guard.Found(…)`), 5 extension calls (`candidates.Nearest()`, `….Truncate()`) and a cast (`((IAuditable)this).Touch()`). 30 ambiguous calls became unresolved: 17 BCL calls whose candidates were all wrong (`List.Add()` ×8, `ToString()` on `int`/`Guid`/`StringBuilder` ×6, LINQ `Count()` ×2, `GetEnumerator()`), and 13 inherited repository calls (`_stock.SaveAsync()`, `_orders.FindAsync()`) whose right target had been among the candidates. Inherited methods need supertype data (issue #321). Go is pending.
- [x] **D4. Locals resolved from another file:** migration 15 ([ADR-035](../01-architecture/adrs/035-function-local-variable-scope.md), #320) keeps a function's variable a candidate only in its own file; the D4 label is now unresolved instead of wrong. Two parser fixes came with it, because removing local candidates exposed name-only matches: a Rust method call inside a macro (`assert!(out.contains(..))`) and a Lua colon call (`a:total()`) are member calls unless the receiver is `self` of a known type, and a bare built-in Rust attribute (`#[ignore]`, `#[should_panic]`) is not a reference. On this repository's index, for every indexed variable name: Rust, 587 wrongly resolved std method calls (`.iter()`, `.clone()`, `.filter()`, `.rev()` resolved to local variables) and 284 ambiguous ones became unresolved; 404 ambiguous references became resolved, to a `use`-imported, path-qualified or same-file item or a `self.` method. Lua, 8 `self:m()` calls became resolved to their own table's method, 2 `ngx.now()` calls became unresolved, and 19 colon calls resolved by name alone became ambiguous: 4 of them were wrong (`self.dict:set` into a test fake) and 15 were plausibly right but unproven (`r:add`, `a:times`). File-level Lua `local`s still cannot be told apart from globals (#321).
