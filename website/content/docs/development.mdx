This page is the entry point for people changing the project's own code. It points to the detailed guides instead of repeating them.

## Where things live

| You want to change… | Look in |
| --- | --- |
| The symbol and relation model, the `LanguageParser` trait | `crates/mct-core` |
| One language's parser | `crates/mct-lang-<name>` |
| Indexing, the SQLite schema, queries | `crates/mct-index` ([Database schema](/docs/schema)) |
| MCP tools, their descriptions and the query cache | `crates/mct-mcp-server` (`server.rs`, `tools.ttc`) |
| The `mct-cli` commands | `crates/mct-cli` |
| The search-quality gate | `crates/mct-eval` |

For the full layout, see [Architecture](/docs/architecture).

## Checks before a pull request

`scripts/unix/check.sh` runs the whole suite in one go: formatting, the tests, the same clippy invocation CI uses, and the `mct-eval` quality gate. Pass `-p <crate>` to check a single crate.

Changing the `LanguageParser` trait, the SQLite schema or an already-published MCP tool signature is a cross-cutting change: open an issue first. See `CONTRIBUTING.md`.

## Adding a language

Each language is one crate. The step-by-step guide is [Adding a language](/docs/extending); the checklist for the pull request (registration, tests, fuzz harness, docs) is the "Adding a new language" section of [`CONTRIBUTING.md`](https://github.com/Zubiarka8/mini-consumes-tokens/blob/main/CONTRIBUTING.md). `scripts/unix/new-language-check.sh <name>` lists whatever is still missing.

Before you open the pull request, update the parser checklists too. They record, with a mark per cell, what each parser extracts today. See [What is implemented](/docs/checklists).

## Adding a library

There are two different things called "library support":

- Teaching the index about the libraries your project uses (manifests, external calls, frameworks): see [Adding library support](/docs/libraries).
- Adding a Rust dependency to this project: see [Adding a library to the project itself](/docs/libraries#adding-a-library-to-the-project-itself).

## Adding an MCP tool

Each tool needs a description block in `tools.ttc` and wiring in several places. `scripts/unix/new-tool-check.sh <tool>` lists every place that still misses it. The format is explained in the "Adding a new MCP tool" section of [`CONTRIBUTING.md`](https://github.com/Zubiarka8/mini-consumes-tokens/blob/main/CONTRIBUTING.md).

## Working with an AI assistant

`rules.md` at the repository root is the single source of rules for AI assistants. It holds the architecture limits, the commands and the rule to explore this repository through its own MCP tools instead of grepping `crates/`.

Point your tool at it and do not copy rules into the tool's own file. `AGENTS.md` and `CLAUDE.md` are one-line pointers to `rules.md`. For Cursor, Copilot or any other tool, make its rules file say to read `rules.md` at the start of each session. Put personal notes that do not belong to the project in `LOCAL_INSTRUCTIONS.md`.

Data that agents, scripts or reports produce or read uses TOON, not JSON, unless an outside format such as `.mcp.json` requires JSON. The MCP tools take `format: toon`.
