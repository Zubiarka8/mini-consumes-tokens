01

Overview — what it is and why it exists

mini-consumes-tokens parses a source repository with tree-sitter into an AST-derived symbol graph — functions, methods, classes, structs, traits, and the relations between them (calls, imports, extends, implements, references) — stored in a single SQLite file. It exposes that graph two ways:

  • ccm-cli — a standalone binary for manual or scripted indexing (CI, pre-commit hooks, coverage checks).
  • ccm-mcp-server — an MCP server over stdio giving Claude Code (or any MCP client) tools to query that graph directly.

The problem it solves: without it, an agent answering "what calls this function?" has to Grep/Read across the repo, paying token cost proportional to file size and false-positive matches. With the index, that question is one exact SQL lookup returning a handful of file:line locations.

What it deliberately does not do: it never executes, evaluates, or type-checks indexed code — parsing is 100% static. It also does not do semantic/type-resolved analysis: relations match by symbol name, not resolved type or import graph (12).

The plugin contract (ccm_core::LanguageParser, crates/ccm-core/src/lib.rs):

rust
pub trait LanguageParser: Send + Sync {
    fn language_id(&self) -> &'static str;               // e.g. "rust" — stored in files.language
    fn file_extensions(&self) -> &'static [&'static str]; // e.g. ["rs"], without the leading dot
    fn parse(&self, file: &SourceFile) -> Result<ParsedFile, ParseError>;
}

parse() must never execute or evaluate the source — a pure AST walk — and must return ParseError::Syntax rather than panic on malformed input, since it runs over arbitrary, untrusted code. Adding a language is exactly: a new crate implementing this trait, plus one registry.register(...) line in each binary — no changes to ccm-core, ccm-index, or the MCP tool surface (16).

Installation

shell
# Option A — from source, inside this repo (identical on Linux/macOS/Windows)
$ cargo install --path crates/ccm-cli
$ cargo install --path crates/ccm-mcp-server

# Option B — from crates.io, once published (see RELEASING.md)
$ cargo install ccm-cli
$ cargo install ccm-mcp-server

Option C — prebuilt binaries (no Rust toolchain required): download the archive for your OS/arch (Linux x86_64/arm64, macOS Intel/Apple Silicon, Windows x86_64) from the GitHub Releases page and put ccm-cli/ccm-mcp-server on your PATH.

shell — verify
$ ccm-cli --help
$ ccm-mcp-server --help

cargo install puts both binaries in ~/.cargo/bin (or %USERPROFILE%\.cargo\bin on Windows) — make sure that directory is on PATH.

mcp-register output

shell
$ ccm-cli --root . mcp-register --name my-project
Registered `my-project` in /abs/path/to/project/.mcp.json

Writes the resolved absolute --root into args — an alternative to claude mcp add (5.1) or hand-editing the JSON from 5.2–5.15 for clients that read the same {"mcpServers": {...}} shape. Reads and re-serializes the existing file if one is present, only inserting/replacing its own name key — any other server already configured there is left untouched. On Windows, Path::canonicalize's \\?\ verbatim-path prefix is stripped before writing, so the value lands as a normal Z:\path\to\project string rather than the raw Win32 extended form.

Exit code is non-zero on any I/O, database, migration, or git-hashing error (13) — but a per-file parse failure is not fatal; it's recorded as an issue and the run continues.

05

Registering the MCP server

ccm-mcp-server is a plain MCP server over stdio — nothing about it is Claude Code-specific. Every client below launches the same binary the same way (command = ccm-mcp-server, args = ["--root", "<absolute-path-to-repo>"]); what differs is the config file's location and root key. Formats below were checked against each project's own docs as of September 2026 — MCP config schemas are still evolving across clients, so if a client rejects the file, check its current docs before assuming this manual is wrong.

5.1 Claude Code

shell
$ claude mcp add mini-consumes-tokens --scope project -- ccm-mcp-server --root "<absolute-path-to-repo>"

# or: ccm-cli's own mcp-register (04) writes the same file directly
$ ccm-cli --root . mcp-register
The help text undersells it. ccm-mcp-server --help lists only 4 tools (find_symbol, find_references, find_calls, find_callers); the server actually registers 9. list_symbols, impact_analysis, reindex, get_indexing_status, and get_file_skeleton were added after that help string was last updated — see 06.

Scope choices

ScopeStored inUse when
--scope localthis machine's local Claude Code config onlypersonal testing
--scope project.mcp.json at repo root — committablethe whole team should be wired up the same way
--scope useryour global Claude Code configyou want it in every project automatically

Resulting .mcp.json (project scope):

json
{
  "mcpServers": {
    "mini-consumes-tokens": {
      "type": "stdio",
      "command": "ccm-mcp-server",
      "args": ["--root", "<absolute-path-to-repo>"],
      "env": {}
    }
  }
}

Decide whether to commit this file: convenient for teammates (auto-wired on git pull), but the absolute --root path is machine-specific, especially on Windows — either use a path valid for every checkout location, or gitignore it and have each person register their own.

Startup indexing behavior

At launch, ccm-mcp-server opens (or creates) the index and runs an incremental reindex automatically — equivalent to ccm-cli reindex without --force. The first registration on a fresh checkout parses the whole repo (seconds to tens of seconds depending on size); later restarts only re-parse changed files.

The approval / restart gotcha. A server added via claude mcp add while a session is already running does not hot-load into it. claude mcp list shows ⏸ Pending approval (run "claude" to approve) and none of its tools are callable until you exit and restart claude in that project, approving the new server when prompted.

5.2 VS Code + GitHub Copilot

Two separate config surfaces exist here — they are not interchangeable, and mixing them up is the most common reason "it doesn't show up":

VS Code itself (Copilot Chat agent mode, or any other extension consuming VS Code's own MCP support) reads .vscode/mcp.json (workspace) or a user-profile mcp.json (global). Root key is "servers" — not mcpServers — and every entry requires an explicit "type":

json
{
  "servers": {
    "mini-consumes-tokens": {
      "type": "stdio",
      "command": "ccm-mcp-server",
      "args": ["--root", "${workspaceFolder}"]
    }
  }
}

${workspaceFolder} expands to the open folder's absolute path, so unlike Claude Code's .mcp.json a committed workspace file doesn't need a hardcoded machine-specific path.

The standalone GitHub Copilot CLI (copilot in a terminal, separate from the VS Code extension) reads its own config at ~/.copilot/mcp-config.json (user-level), root key "mcpServers", type "local":

json
{
  "mcpServers": {
    "mini-consumes-tokens": {
      "type": "local",
      "command": "ccm-mcp-server",
      "args": ["--root", "<absolute-path-to-repo>"],
      "tools": ["*"]
    }
  }
}
As of 2026 the Copilot CLI no longer reads .vscode/mcp.json for its own sessions (an earlier compatibility path was removed). If copilot can't see a server that VS Code itself sees fine, this is why — each surface needs its own file.

5.5 Codex CLI (OpenAI)

~/.codex/config.toml (user) or a project-scoped .codex/config.toml for trusted projects — TOML, not JSON, one table per server under the snake_case key mcp_servers:

toml
[mcp_servers.mini-consumes-tokens]
command = "ccm-mcp-server"
args = ["--root", "<absolute-path-to-repo>"]

The transport is inferred from which key is present (command → stdio, url → HTTP) — don't mix both in the same table. The Codex IDE extension reads the same config.toml, so one entry covers both.

5.7 Claude Desktop

The desktop app — a separate product from the Claude Code CLI in 5.1, with its own config file: ~/Library/Application Support/Claude/claude_desktop_config.json (macOS) or %APPDATA%\Claude\claude_desktop_config.json (Windows). Root key "mcpServers", no "type" field:

json
{
  "mcpServers": {
    "mini-consumes-tokens": {
      "command": "ccm-mcp-server",
      "args": ["--root", "<absolute-path-to-repo>"]

Reach the file without hand-navigating the filesystem: Claude menu (macOS menu bar, or the app's own menu on Windows — not the in-chat settings) → Settings → Developer → Edit Config. This creates the file if it doesn't exist yet.

5.8 Windsurf (Codeium)

~/.codeium/windsurf/mcp_config.json (macOS/Linux) or %USERPROFILE%\.codeium\windsurf\mcp_config.json (Windows), reachable from the Cascade panel's hammer/MCP icon → Configure. Root key "mcpServers", same shape as Claude Desktop's — no "type" field for a stdio entry:

json
{
  "mcpServers": {
    "mini-consumes-tokens": {
      "command": "ccm-mcp-server",
      "args": ["--root", "<absolute-path-to-repo>"]

Cascade caps tool count at 100 total, across every connected server. This server's 9 tools are nowhere near that limit alone, but on a config with many other servers already registered, individual tools can be toggled off per-server (unlike Cursor, which only toggles whole servers) to stay under the cap.

Zed has no dedicated MCP config file — entries go under the "context_servers" key in Zed's own settings.json (open it with the zed: open settings command), alongside every other editor setting:

json

5.10 Cline (VS Code extension)

cline_mcp_settings.json under VS Code's per-extension global storage: ~/Library/Application Support/Code/User/globalStorage/saoudrizwan.claude-dev/settings/cline_mcp_settings.json (macOS) or %APPDATA%\Code\User\globalStorage\saoudrizwan.claude-dev\settings\cline_mcp_settings.json (Windows). Reachable in-editor via the Cline panel's MCP Servers icon → Configure → Configure MCP Servers, which opens the file directly instead of requiring that path be typed by hand. Root key "mcpServers", same base shape as Claude Desktop's, plus two Cline-specific optional fields:

json
{
  "mcpServers": {
    "mini-consumes-tokens": {
      "command": "ccm-mcp-server",
      "args": ["--root", "<absolute-path-to-repo>"],
      "disabled": false,
      "autoApprove": []
    }
  }
}

disabled/autoApprove are Cline additions on top of the common shape — omit both and the server is enabled with no tools auto-approved, same as every other client here.

5.11 Continue.dev

config.yaml (global ~/.continue/config.yaml, or a project's .continue/config.yaml) — YAML, and mcpServers is a list, not a keyed object like every other client in this section:

yaml
mcpServers:
  - name: mini-consumes-tokens
    command: ccm-mcp-server
    args:
      - "--root"
      - "<absolute-path-to-repo>"
The older config.json format is deprecated in favor of config.yaml. Separately, Continue also reads standalone files under .continue/mcpServers/ — and will accept a claude_desktop_config.json-shaped (keyed-object) JSON file dropped in that directory as-is, without conversion to the list form above.

5.14 OpenHands

config.toml, under an [mcp] table with stdio_servers as an array of inline tables — TOML, but a different shape from Codex CLI's one-table-per-server style in 5.5:

toml
[mcp]
stdio_servers = [

]

name is required alongside command/args here, unlike Codex where the server's name is the TOML table key itself. Servers can also be added from OpenHands' own Settings UI instead of hand-editing config.toml.

5.15 Any other MCP client

The pattern generalizes: point command at ccm-mcp-server (full path if it isn't on the client's PATH) and pass --root <absolute-path-to-repo> via args. Two gotchas apply regardless of client:

  1. --root must be absolute. A relative path resolves against whatever working directory the client happens to spawn the process from — often not the repo root, and not consistent across clients.
  2. No client here changes the file-watching behavior described in 10. ccm-mcp-server only reindexes at its own startup; after a git pull or branch switch, ask the agent to call reindex, or restart the server.
06

MCP tools — full reference

Every description below is the exact text the model sees (from crates/ccm-mcp-server/src/server.rs) — it drives which tool Claude picks, so it's worth reading verbatim if a query isn't resolving how you expect. All name parameters require an exact match (trimmed, case-sensitive, no fuzzy/regex) on symbols.name or relations.to_name/from_symbol.name; an empty name returns an invalid_params error before any query runs.

The five result-returning tools (find_symbol, find_references, find_calls, find_callers, impact_analysis) all accept an optional limit: number parameter, defaulting to 50 (DEFAULT_RESULT_LIMIT in server.rs) when omitted — generous enough that a typical handful-to-dozens of hits is never truncated, but bounded so a symbol with hundreds of matches in a large repo can't blow up a single response past what the grep baseline this project replaces would cost. Raise it explicitly if you expect more hits and want them all in one call.

list_symbols — discovery

"DISCOVERY, not a precise lookup — use this FIRST when you don't know a symbol's exact name yet. Lists symbol definitions (name, kind, line range) found under `path`: a single file (exact path) or a directory/crate (a path with no file extension, matched as a prefix), optionally narrowed to one symbol `kind` and/or one `language`. Answers 'what functions/structs/classes does this file or crate have' without already knowing a name. Do NOT use this to locate one already-known symbol precisely, or to jump straight to its definition — use find_symbol for that; list_symbols is the discovery step that feeds find_symbol/find_references/find_calls/find_callers/impact_analysis, not a replacement for them."

Params: path: string (a file path matched exactly, or a directory/crate path with no file extension matched as a prefix), kind: string (optional), language: string (optional), limit: number (optional, default 50).

Output: one line per symbol — path:line-end_line [language] kind name, sorted by relative_path then line.

find_symbol — atomic

"ATOMIC lookup. Find the definition location(s) of a symbol by exact name, across every indexed language in this repository (including polyglot projects). Use this instead of grepping files to answer 'where is X defined'. Do NOT use this to find who calls or references a symbol — use find_callers (direct callers only) or find_references (every reference) instead."

Params: name: string, limit: number (optional, default 50).

sql
SELECT s.name, s.kind, f.language, f.relative_path, s.line, s.column, s.parent
FROM symbols s JOIN files f ON f.id = s.file_id
WHERE s.name = ?1
ORDER BY f.relative_path, s.line
output
2 definition(s) of `LanguageParser`:
crates/ccm-core/src/lib.rs:39:1 [rust] trait LanguageParser
...

Empty result: No symbol named \`X\` found in the index. Can return multiple hits — e.g. every language's own parse method, since names aren't namespaced across files.

find_references — atomic

"ATOMIC lookup. Find every place a symbol is referenced: calls, imports, extends/implements, and plain references — the broadest reference search. Do NOT use this when you only want the functions that directly call a function — use find_callers instead, which is narrower and answers that question directly. Do NOT use this to find a symbol's own definition — use find_symbol."

Params: symbol: string — matches relations.to_name = ?1 across every relation kind, unfiltered; limit: number (optional, default 50); depth: number (optional, default 1, clamped to [1, 32]) — walks the reference graph breadth-first beyond the direct hit, so depth: 2 also includes referrers-of-referrers, cycle-guarded by a visited-name set (see crates/ccm-index/src/traversal.rs); offset: number (optional, default 0) — skips this many leading results before applying limit.

Output: N reference(s): then path:line:col [language] fromSymbol --kind--> toName per hit, with a trailing [depth N] tag beyond depth 1 (omitted for direct hits, so output is byte-identical to before depth existed when it's never passed).

find_calls — atomic

"ATOMIC lookup. Find the functions/methods called by the given function — its callees. Answers 'what does this function call'. Do NOT use this to find who calls the function — that's the inverse question, answered by find_callers."

Params: function: string — WHERE caller.name = ?1 AND r.kind = 'calls'; limit: number (optional, default 50); depth: number (optional, default 1, clamped to [1, 32]) — walks the call graph forward beyond the direct hit; offset: number (optional, default 0).

find_callers — atomic

"ATOMIC lookup. Find the functions/methods that call the given function — its callers. Answers 'who calls this function'; the inverse of find_calls. Do NOT use this for a broader reference search (imports, extends/implements, non-call references) — use find_references instead. If you're about to change or remove this function and want its full blast radius (callers + references + likely tests) in one call, use impact_analysis instead of calling this separately."

Params: function: string — WHERE r.to_name = ?1 AND r.kind = 'calls', the exact inverse of find_calls; limit: number (optional, default 50); depth: number (optional, default 1, clamped to [1, 32]) — walks the call graph backward beyond the direct hit; offset: number (optional, default 0).

impact_analysis — composite

"COMPOSITE (internally combines find_callers + find_references + a test-name heuristic — you do not need to call those separately). Reports everything a change to `symbol` could break: its direct callers, its full reference set (calls/imports/extends/implements/plain), and which of those look like tests (name starting with `test`). Use this before editing or removing a symbol to gauge blast radius in one call. Do NOT use this for a plain lookup of only direct callers or only references — that's cheaper via find_callers or find_references alone, and this tool's output is more verbose."

Params: symbol: string; limit: number (optional, default 50 — applied independently per section: callers, references, and affected tests are each capped separately, not combined); depth: number (optional, default 1, clamped to [1, 32], applied to both the caller and reference BFS walks); offset: number (optional, default 0, applied independently per section). Runs the same BFS find_callers/find_references walks under the same lock, then computes affected_tests by filtering both for names matching looks_like_test_name (case-insensitive starts_with("test")/"test_"), deduped by name.

output shape
Impact analysis for `Symbol`:
  N direct caller(s)
  M reference(s) total (calls/imports/extends/implements/plain)
  K likely affected test(s)

Likely affected tests:
  path:line:col [language] testFnName
  ...

Direct callers:
  path:line:col [language] callerName
  ...

All references:
  path:line:col [language] fromSymbol --kind--> symbol
  ...

If both sets are empty: Nothing else in the index references this symbol.

"INDEX ADMINISTRATION, not a search tool. No params. Same content and shape as ccm-cli status (04).

get_file_skeleton — discovery

"TOKEN-SAVING module overview. Returns a file's top-level declarations (functions, classes, structs, interfaces, types) with bodies collapsed to `// ...` — up to ~90% fewer tokens than reading the whole file when you just need its shape. Brace-delimited languages (Rust, Go, Java, C++, C#, PHP, JS/TS, Kotlin) get precise body elision; other languages (e.g. Python, Lua, Bash, PowerShell) get a best-effort declaration-line-only rendering. Nested members (e.g. methods inside a class) are NOT shown individually — a class/struct/interface collapses to one block regardless of what's inside it. Do NOT use this for a directory/crate — it takes a single file path; use list_symbols for that. Do NOT use this when you need a symbol's actual implementation, not just its shape — use find_symbol to locate it, then read the file directly."

Param: path: string — a single file, exact path; rejected with invalid_params if it looks like a directory/crate prefix — use list_symbols first if you don't already know which file you need.

Mechanics: reads the file's own source text off disk (same traversal guard the indexer's walk uses — a path resolving outside the project root is refused), takes every top-level symbol from list_symbols for that file, and renders each one of two ways: brace-delimited languages (Rust, Go, Java, C++, C#, PHP, JS/TS, Kotlin) get their body collapsed to // ... between the matching braces; every other language falls back to showing only the declaration line. Nested members are never expanded individually.

Empty result: No top-level symbols found in \`path\` to build a skeleton from.

Server self-description (sent verbatim in the MCP initialize response — this is what nudges Claude toward these tools over Read/Grep/Glob):

"Indexes this repository's source code (any of the supported languages, including polyglot repos) into a symbol graph. Prefer these tools over reading whole files with grep or a file reader when you need to locate a definition or understand call relationships — it costs far fewer tokens. list_symbols is the discovery tool: use it first when you don't know a symbol's exact name, to list what a file or directory/crate contains. 07

How indexing actually works

Step by step, from crates/ccm-index/src/indexer.rs::reindex:

  1. Walk the project root with walkdir::WalkDir, skipping directories.
  2. Symlink/escape guard: each entry is canonicalize()d; failure (broken symlink, race) or a canonical path outside the root — both skipped silently. A symlink can never make the indexer read outside the project root.
  3. Path normalization: the relative path is rebuilt with forward slashes on every OS, so the index is portable between a Windows checkout and a Linux CI runner.
  4. Exclusion check (09) — excluded paths are skipped but kept in seen_paths, so a previously-indexed row is cleaned up if exclude patterns later change.
  5. Extension lookup via registry.for_extension(ext). No parser registered? If the extension is in KNOWN_PENDING_LANGUAGES (swift, rb→ruby), it's recorded as an unsupported_language issue. Any other unrecognized extension (docs, images, lockfiles, .lua) is skipped with zero record — this is why a repo with .lua files wouldn't show "lua" as unsupported even though ccm-lang-lua isn't wired in.
  6. Read + hash: I/O error → skip. Content hash is a git blob SHA-1 via git2::Oid::hash_object(ObjectType::Blob, &bytes) — works outside an actual git repo; it's just git's hashing algorithm reused for change detection.
  7. Incremental skip: if the stored hash for this path matches and --force/force:true wasn't passed, count as files_unchanged and skip entirely — no re-parse, no writes.
  8. UTF-8 check: invalid UTF-8 (binary file sharing a supported extension) is skipped silently, not recorded as a syntax error.
  9. Parse via the matching LanguageParser. Success → written in one transaction (below). ParseError::Syntax → recorded as a syntax_error issue with line/message; the file's previous data (if any) is left untouched until it parses successfully again.
  10. Per-file write transaction (write_parsed_file): upsert the files row; delete existing symbols for that file_id (cascades to relations) and any stale index_issues row; insert every symbol, building a local-id→row-id map; insert every relation, with to_symbol_id resolved best-effort by name only (first match, arbitrary on ambiguity — and not what powers any lookup query, which all match on text columns directly); commit.
  11. Deletion sweep after the whole walk: any files row not in seen_paths this run is deleted (cascades), plus orphaned index_issues rows — this is how a deleted or moved file disappears from the index.
  12. Timestamp: index_meta.last_indexed_at upserted with the current Unix time.

Concurrency: the MCP server wraps the whole Index in a tokio::sync::Mutex — one query or reindex at a time, no concurrent access from overlapping tool calls.

Database schema — full reference

File: <root>/.ccm-index/index.sqlite3. Applied via a single rusqlite_migration migration (from crates/ccm-index/src/schema.rs):

sql — full ddl
CREATE TABLE files (
    id              INTEGER PRIMARY KEY,
    relative_path   TEXT NOT NULL UNIQUE,
    language        TEXT NOT NULL,      -- "rust", "python", "javascript_typescript", ...
    content_hash    TEXT NOT NULL,      -- git blob SHA-1 of the file's bytes
    last_indexed_at INTEGER NOT NULL    -- unix seconds
);
CREATE INDEX idx_files_language ON files(language);

CREATE TABLE symbols (
    id       INTEGER PRIMARY KEY,
    file_id  INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
    name     TEXT NOT NULL,
    kind     TEXT NOT NULL,   -- function|method|class|struct|interface|enum|trait|type_alias|module|variable|constant|field|element|rule
    parent   TEXT,            -- enclosing symbol's name, if any; NULL for top-level
    line     INTEGER NOT NULL,
    column   INTEGER NOT NULL,
    byte_len INTEGER NOT NULL
);
CREATE INDEX idx_symbols_name ON symbols(name);
CREATE INDEX idx_symbols_file ON symbols(file_id);

CREATE TABLE relations (
    id             INTEGER PRIMARY KEY,
    from_symbol_id INTEGER NOT NULL REFERENCES symbols(id) ON DELETE CASCADE,
    kind           TEXT NOT NULL,   -- calls|imports|extends|implements|references
    to_name        TEXT NOT NULL,   -- target name as written in source (may not resolve to a row)
    to_symbol_id   INTEGER REFERENCES symbols(id) ON DELETE SET NULL,  -- best-effort, unused by queries
    line           INTEGER NOT NULL,
    column         INTEGER NOT NULL,
    byte_len       INTEGER NOT NULL
);
CREATE INDEX idx_relations_from ON relations(from_symbol_id);
CREATE INDEX idx_relations_to_name ON relations(to_name);
CREATE INDEX idx_relations_kind ON relations(kind);

-- Full-text search over symbol names. Not exposed by any CLI/MCP tool today
-- (find_symbol uses exact `=` match) — query it directly for fuzzy lookups, see 11.
CREATE VIRTUAL TABLE symbols_fts USING fts5(name, content='symbols', content_rowid='id');
-- + triggers symbols_ai/ad/au keep it in sync on insert/delete/update.

-- Files skipped during indexing (distinct from files indexed successfully).
CREATE TABLE index_issues (
    id            INTEGER PRIMARY KEY,
    relative_path TEXT NOT NULL,
    issue_kind    TEXT NOT NULL,   -- 'unsupported_language' | 'syntax_error'
    detail        TEXT NOT NULL,   -- language name, or "line N: message"
    detected_at   INTEGER NOT NULL,
    UNIQUE(relative_path, issue_kind)
);

CREATE TABLE index_meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL   -- currently only 'last_indexed_at'
);

-- Declared dependencies from a manifest file, matched by file NAME (not
-- extension, not through any LanguageParser — a manifest isn't source code
-- to symbol-index). Populated by ccm-index/src/manifests.rs. A second
-- migration, added after the table above, so an existing index gets this
-- table added instead of needing a fresh one.
CREATE TABLE dependencies (
    id            INTEGER PRIMARY KEY,
    manifest_path TEXT NOT NULL,
    language      TEXT NOT NULL,   -- ecosystem the manifest belongs to
    name          TEXT NOT NULL,
    version       TEXT,            -- absent for path/git deps, or `{ workspace = true }` entries
    UNIQUE(manifest_path, name)
);
CREATE INDEX idx_dependencies_manifest ON dependencies(manifest_path);
CREATE INDEX idx_dependencies_name ON dependencies(name);
ColumnValues you'll see
symbols.kindfunction, method, class, struct, interface, enum, trait, type_alias, module, variable, constant, field, element (an HTML/XML/XAML element with an id-like attribute), rule (a simple CSS selector)
relations.kindcalls, imports, extends, implements, references

Design note baked into the schema: one shared table per concept across all languages — no per-language tables. symbols/relations carry a language column via their files join instead, which is why adding a language plugin never requires a schema migration, even HTML/CSS/XML/XAML: element/rule needed two new SymbolKind variants in ccm-core (nothing else fit an HTML element or a CSS selector), but since kind is a plain string column, the table itself didn't change.

Dependency manifests recognized today: Cargo.toml ([dependencies]/[dev-dependencies]/[build-dependencies], plus [workspace.dependencies] on a workspace root), package.json (dependencies/devDependencies/peerDependencies/optionalDependencies), requirements.txt (one requirement per line, version kept as the constraint text written — ">=2.0,<3.0", not resolved to one version), go.mod (require block and single-line forms; go.sum not read — direct dependencies only). Unlike source files, a manifest is re-parsed on every reindex, not skipped when unchanged — they're few and small, not worth a second incremental-skip mechanism. Exposed via get_indexing_status's "Dependencies detected" section (06), not a separate MCP tool — deliberate, to keep the tool count small (9 total, 06) rather than growing one tool per data point.

File exclusion rules

Hardcoded in crates/ccm-index/src/exclude.rs as DEFAULT_EXCLUDE_PATTERNS, matched with globset against the forward-slash relative path:

**/.env             **/.env.*           **/*.pem            **/*.key
**/secrets/**       **/secret/**        **/credentials.json **/.aws/**
**/node_modules/**                                          (Node/JS)
**/appsettings.*.json  **/*.pfx  **/*.snk                    (.NET)
**/gradle.properties                                         (Java/Gradle/Maven)
**/*.env.local  **/config/secrets.yaml                        (Go / Viper-style config)
**/.git/**  **/target/**  **/.ccm-index/**                 (VCS / build output / the index itself)

These exist so a fresh install never accidentally indexes a secret — opt-out is the design, not opt-in. ExcludeSet::new(extra_patterns) accepts a list to widen (never narrow) this set at the API level, but neither ccm-cli nor ccm-mcp-server currently exposes a flag or config file to supply extra_patterns — both call ExcludeSet::default() unconditionally. If you need to exclude something project-specific today, your only lever is renaming/moving the file to match an existing pattern, or contributing a config surface.

10

Managing the index day to day

When to just let it run: the MCP server reindexes incrementally at every startup — for normal day-to-day editing, you don't need to do anything.

When to run reindex manually:

  • After a git pull/branch switch that changed many files while the MCP server stayed running (it only reindexes at startup, not via a file-watcher).
  • After moving/renaming a lot of files.
  • If status/get_indexing_status shows stale-looking counts.

When to use --force/force: true: only if you suspect internal inconsistency (manual .sqlite3 edits, or a version upgrade that changed hashing/parsing behavior) — normal edits are always picked up incrementally, since comparison is content-hash based, not mtime-based (touching a file without changing its bytes does not trigger a re-parse).

shell — rebuild from scratch
$ rm -rf .ccm-index
$ ccm-cli --root . init

Safe at any time — the index is a pure derived artifact; deleting it loses nothing reconstructible from source.

Committing to git: never. .ccm-index/ should be gitignored. It's large relative to source (this repo's own index is ~848 KiB for 161 files/1,445 symbols), regenerates deterministically, and is meaningless to diff.

Querying the database directly

No sqlite3 CLI needed — Python's standard library works everywhere:

python
$ python3 -c "
import sqlite3
conn = sqlite3.connect('.ccm-index/index.sqlite3')
cur = conn.cursor()
cur.execute(\"SELECT name, kind, file_id FROM symbols WHERE name = 'YourSymbol'\")
print(cur.fetchall())
"

Useful ad hoc queries:

sql — cookbook
-- Everything indexed for one file
SELECT s.name, s.kind, s.line FROM symbols s
JOIN files f ON f.id = s.file_id
WHERE f.relative_path = 'crates/ccm-core/src/lib.rs' ORDER BY s.line;

-- Every relation kind used in the repo (sanity check)
SELECT DISTINCT kind FROM relations;

-- Fuzzy/substring symbol search (no CLI/MCP tool exposes this — direct FTS5 query)
SELECT s.name, s.kind FROM symbols_fts
JOIN symbols s ON s.id = symbols_fts.rowid
WHERE symbols_fts MATCH 'Pars*';

-- Every file that failed to parse or is in an unsupported language
SELECT * FROM index_issues;

-- Coverage per language, same numbers `status` reports
SELECT f.language, COUNT(DISTINCT f.id), COUNT(s.id)
FROM files f LEFT JOIN symbols s ON s.file_id = f.id
GROUP BY f.language;

If the sqlite3 CLI is available on your system, the same queries work with sqlite3 .ccm-index/index.sqlite3 "SELECT ...".

Known limitations and deliberate simplifications

  • Name-based relations, not type-resolved. find_calls/find_callers/find_references match on plain text. Two unrelated functions named parse in different files/languages are indistinguishable by name alone — a query for "callers of parse" returns every caller of any parse, disambiguated only by reading relative_path/language in the result. Architecture, not a bug — real overload/import resolution per language is a much larger scope.
  • to_symbol_id is best-effort and unused by queries. Populated via SELECT id FROM symbols WHERE name = ?1 LIMIT 1 (first match, arbitrary on ambiguity) but no shipped query joins on it.
  • Test detection is a naming heuristic, not framework-aware. impact_analysis's "likely affected tests" is name.to_lowercase().starts_with("test") — no recognition of #[test], pytest fixtures, JUnit annotations, etc.
  • Lua is implemented but not wired in. ccm-lang-lua is a full, tested LanguageParser kept as an acceptance test proving the plugin architecture — but it's not in either binary's build_registry(). .lua files are silently skipped, not even reported as "unsupported" (since lua isn't in KNOWN_PENDING_LANGUAGES).
  • CSS only indexes simple selectors. .foo/#foo alone become Rule symbols; compound selectors (div.foo) and combinators (.a .b, #id > .c) are skipped — matching which elements they actually reach needs a DOM, not an AST.
  • Plain XML never emits relations. ccm-lang-xml indexes id/name/Name-attributed elements (case-exact, in that priority) as Element symbols for structure only — there's no dialect-generic convention to cross-reference (a Maven POM and an Android layout mean completely different things by their attributes).
  • Markdown is Phase 1 — headings only, no relations. ccm-lang-md indexes ATX headings (#…######) as Element symbols, nested via tree-sitter-md's own section structure (a heading's parent is the nearest enclosing section's heading, resolved by the grammar itself — no manual level-counting stack). Deliberately out of scope for this phase: internal links, anchors, setext headings, lists, tables, and code blocks — it emits zero RelationKinds. Unlike ccm-lang-xml, a heading-less document produces zero symbols, not a synthetic root.
  • XAML's event-handler cross-referencing is a bounded allowlist, not a heuristic. EVENT_ATTRIBUTE_NAMES in ccm-lang-xaml lists ~40 common WPF/UWP/WinUI/MAUI/Avalonia event names (Click, Loaded, SelectionChanged, ...) — an attribute outside that list, even if it wires up a real code-behind handler, won't produce a References relation.
  • ccm-lang-powershell doesn't index classes. class Foo { ... } and its methods are invisible to the index — only function-style definitions are, since the scope this plugin was built for is systems-scripting .ps1/.psm1 files, where classes are rare.
  • ccm-lang-bash/ccm-lang-powershell only index top-level variables, and every command/cmdlet invocation is recorded as an unresolved Calls relation regardless of whether it turns out to be a local function or an external program — same "resolved downstream, matched by name" precedent as every other language here.
  • ccm-lang-php reuses SymbolKind::Trait for PHP's trait keyword, the same tag ccm-lang-rust uses for Rust traits — the two are semantically different (a PHP trait is a code-inclusion mixin, not an interface-like contract), sharing only the tag name, not the meaning.
  • ccm-lang-php records use TraitName; (trait composition) as a RelationKind::Implements relation on the enclosing class/enum — the closest existing relation kind, though not a perfect fit. ccm-core has no dedicated "uses/composes" relation kind today.
  • KNOWN_PENDING_LANGUAGES is a short, hardcoded list (swift, ruby) — any other genuinely unsupported language's files are skipped with zero visibility in status.
  • Exclude patterns aren't user-configurable from either binary today (09), despite the underlying API supporting it.
  • No file-watching. The index only updates on an explicit reindex or MCP server startup.
  • Binary files sharing a supported extension are silently skipped, not reported as a parse failure — they fail the UTF-8 check before parsing is attempted.
  • One index per --root, single-process, single in-flight operation. The MCP server serializes all tool calls behind one tokio::Mutex<Index> — fine for interactive use, not built for high-concurrency multi-client access.

14

Security model

  • Static parsing only. LanguageParser::parse() never executes or evaluates file contents — every parser is a pure tree-sitter AST walk. Indexing an untrusted repository runs none of its code.
  • All SQL is parameterized. Every query binds symbol names via ?1-style placeholders — never string-interpolated (confirmed in crates/ccm-index/src/queries.rs, called out explicitly in source comments) — no SQL injection surface from name lookups.
  • Symlink escape prevention. Every walked entry is canonicalized and rejected if it resolves outside the project root (07) — a malicious symlink can't make the indexer touch files elsewhere.
  • Secret-pattern exclusion by default, opt-out not opt-in (09) — a fresh install never indexes .env, *.pem, *.key, cloud credential directories, etc.
  • No network calls, zero telemetry — indexing and querying are entirely local/offline.

Extending it: adding a language

  1. New crate, e.g. crates/ccm-lang-<lang>, depending on ccm-core and the relevant tree-sitter-<lang> grammar crate.
  2. Implement ccm_core::LanguageParser (02): language_id(), file_extensions(), parse() — walk the AST and emit SymbolRecords and SymbolRelations. Use ccm-lang-rust/src/lib.rs or ccm-lang-python/src/lib.rs as the reference pattern.
  3. Register it in both places — ccm-mcp-server/src/registry.rs and ccm-cli/src/main.rs::build_registry — one registry.register(Arc::new(YourLangParser)) line each. Nothing else in ccm-core/ccm-index/ccm-mcp-server changes.
  4. Add idiomatic-syntax fixtures in crates/ccm-lang-<lang>/tests/parse.rs (generics, decorators, whatever that language's equivalents are).
  5. Update the language coverage table in README.md and internal/checklist.md.
  6. Run the token-savings benchmark for the new language once it exists (currently unimplemented workspace-wide, tracked in internal/checklist.md).
