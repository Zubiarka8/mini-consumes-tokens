## Open decisions

1. **Type resolution:** the MVP uses AST parsing (tree-sitter) for the eight languages; real LSP resolution is a later improvement. This does not block the completion criteria for this session.
2. **Secret exclusion patterns:** a shared baseline is implemented in `mct-index/src/exclude.rs` (`.env`, `*.pem`, `*.key`, `secrets/`, `credentials.json`, `.aws/`, `node_modules/`, `appsettings.*.json`, `*.pfx`, `*.snk`, `gradle.properties`, `.git/`, `target/`, `.mct-index/`, plus `*.env.local` and `config/secrets.yaml` for Go added in that session). **Go was resolved in that session** (see the Go row in "Language coverage" and new tests in `mct-index/tests/exclude.rs`). Ruby and Swift are **deferred, not active work**: no language crate is planned yet, so there is no concrete convention to review. **PHP remains active and unresolved.** An earlier version of this entry incorrectly said that no PHP secret conventions had been identified; `ROADMAP.md` §2 already named `wp-config.php` and `config/database.php` before `mct-lang-php` existed. The only PHP-related addition so far is `**/vendor/**` (Composer's dependency directory) in `DEFAULT_EXCLUDE_PATTERNS`; this excludes third-party dependencies, not secrets, just like `node_modules/` (test: `mct-index/tests/exclude.rs::php_composer_vendor_directory_is_excluded`). Both actual PHP secret patterns remain unimplemented.
3. **Defer Go `find_implementations` until LSP type resolution.** Go interfaces are structural (they are implemented by a method set, not an `implements` keyword), and the compiler determines conformance; an AST-only matching heuristic would be unreliable. `mct-lang-go` exposes explicit call/import relations and indexes interface symbols and declared methods (see the Go row). Revisit with the general LSP decision (#1).
4. **`mct-lang-html` does not recognize template engines embedded in `.html`** (Django Template Language, Jinja2, and others reusing the `.html` extension). This was **empirically verified in that session** using a realistic Django template (`{% extends %}`, `{% for %}`, `{{ variable }}`, `{% url %}`, `{% include %}`) in a disposable test that was removed afterward, following the same pattern as other probes. `tree-sitter-html` **reports no syntax error** because it is permissive and treats `{% %}`/`{{ }}` outside tags as plain text. The file therefore appears to index "without problems" in `get_indexing_status`, but template syntax produces incorrect symbols/relations: `id="item-{{ item.id }}"` is indexed literally, braces included, as an `Element` name; `class="{% if user.is_authenticated %}active{% endif %}"` is split on spaces into six meaningless `References` (`.{%`, `.if`, `.user.is_authenticated`, `.%}active{%`, `.endif`, `.%`). Meanwhile, Django semantics disappear silently: `{% extends "base.html" %}` and `{% include "partials/footer.html" %}` produce no `Imports` relations (unlike real `<link>`/`<script src>` tags), and `{% block %}`/`{% for %}` produce no symbols. Real HTML outside template tags (elements, genuine `id`/`class`, `<link>`, `<script>`) still indexes correctly; the problem is limited to template syntax. **A user decision is pending** between (a) documenting this as a known limitation in MANUAL §12 without changing behavior, or (b) implementing actual handling, such as detecting template syntax and excluding/warning about those files or adding a dedicated crate/heuristic. No source code was changed for this finding; it was detection and reporting only.

## Dependency-manifest detection

Decision (2026-09-14): at the user’s request to include libraries/frameworks in the database, we first verified that `files.language` already existed per file (an indexed column used by all queries), so no change was needed there. The new feature is detection of **declared dependencies**, scoped with the user in two questions: (1) coverage — **Rust + JS/TS + Python + Go**, one standard manifest per language (`Cargo.toml`/`package.json`/`requirements.txt`/`go.mod`); Java/C# were excluded because Maven versus Gradle multiplies formats and Gradle is a Groovy/Kotlin DSL, not declarative, so parsing it reliably would require an interpreter. (2) exposure — **inside `get_indexing_status`** as a new “Dependencies detected” section, not a new tool, preserving the earlier 6–8-tool design decision.

**Implementation**: Added a `dependencies` table (`manifest_path`, `language`, `name`, nullable `version`) in a **second migration** in `schema.rs` (kept separate from the first so existing `.mct-index/index.sqlite3` databases receive it on reindex instead of requiring recreation). Detection deliberately lives **outside** `LanguageParser` because manifests are not source code to index as symbols; new module `mct-index/src/manifests.rs` provides `manifest_language(file_name)` (matches the **exact filename**, not extension) and `parse_manifest` (dispatches by format). `Cargo.toml` uses the `toml` crate. A concrete parsing pitfall found this session: `s.parse::<toml::Value>()` fails with “unexpected content, expected nothing” because `Value::from_str` expects a single value, not a whole document; parse as `s.parse::<toml::Table>()`, confirmed with a disposable example before tests. `package.json` uses generic `serde_json::Value` (no `Deserialize` structs); `requirements.txt`/`go.mod` are parsed line by line because their formats do not warrant a grammar dependency, matching the project’s grammar-versus-plain-text criterion. Wired into the existing `reindex()` tree-walk loop: each recognized manifest is read, parsed, and rewritten (`DELETE` + `INSERT` by `manifest_path`) on every reindex; it is **not skipped by unchanged hash** like other files (deliberately, because manifests are few/small and a second incremental-skip mechanism is not worthwhile). Deleted/excluded manifests are cleaned up through `remove_missing_manifests`, matching `remove_missing_files`.

New `mct-index` dependencies: `toml = "1"`, `serde_json = "1.0.151"` (the same version already used by `mct-mcp-server`).

**Tests**: Seven unit tests in `manifests.rs` (one per format, Cargo `[workspace.dependencies]` table, missing version for a path dependency, and malformed manifest returns empty rather than panicking) + four integration tests in `mct-index/tests/manifests.rs` through the real `reindex`→`status` pipeline (one manifest appears in `status.dependencies`, multiple manifests stay separate, deleting a manifest removes it on the next reindex, editing one refreshes its dependencies—explicitly verifying the no-hash-skip behavior above). **Dogfooding**: ran `cargo run -p mct-cli -- --root . status` against this repository; it correctly detected all 24 workspace `Cargo.toml` files (root + 12 crates + 11 `fuzz/` manifests). A `{ workspace = true }` dependency (e.g. `mct-core` in each crate) appears without a version because the actual version is in the root `Cargo.toml`, scanned as its own manifest. This output was manually checked, not only covered by synthetic tests.

Exposed in `get_indexing_status` (`mct-mcp-server/src/format.rs::index_status`) and `mct-cli status` (`mct-cli/src/main.rs::print_status`), with identical text in both following the existing `IndexStatus` pattern. The MCP tool description now mentions dependencies. `MANUAL.md`/`MANUAL.html` were updated in schema §08 (table, recognized-manifest note, and `status` example), and `README.md` in its Status section. `git diff` verified **zero changes in `mct-core/src/`**: the `LanguageParser` trait and `SymbolKind`/`RelationKind` were untouched; the feature lives in `mct-index` and downstream presentation. `cargo test --workspace` (zero failures) and restrictive workspace Clippy (`-D warnings -D clippy::unwrap_used -D clippy::expect_used -D clippy::panic`, zero findings) were re-run after the full change.

## MCP tool design

Design criterion applied this session: keep the tool count to 6–8, classify each as Atomic / Composite / Index administration, and add anti-ambiguity guidance (“when NOT to use this; use Y instead”) where similar tools could be confused.

| Tool | Category | Ambiguity resolved against |
|---|---|---|
| `find_symbol(name)` | Atomic | Says not to use it for callers/references → points to `find_callers`/`find_references` |
| `find_references(symbol)` | Atomic | Says not to use it when only direct callers are needed → points to `find_calls` |
| `find_calls(function)` | Atomic | Says it is the inverse of `find_callers` |
| `find_callers(function)` | Atomic | Says it is the inverse of `find_calls`; says not to use it for broad reference searches → points to `find_references`; says not to use it for a complete blast radius → points to `impact_analysis` |
| `impact_analysis(symbol)` | **Composite** (implemented in this session) | Internally combines `find_callers` + `find_references` + a test-name heuristic (`test`/`test_*`); composed in Rust (`mct-mcp-server/src/server.rs::impact_analysis`), not delegated to the agent. Says not to use it for a simple lookup → using `find_callers`/`find_references` alone is cheaper |
| `reindex(force)` | Index administration | Description explicitly marked "INDEX ADMINISTRATION, not a search tool" |
| `get_indexing_status()` | Index administration | Description explicitly marked "INDEX ADMINISTRATION, not a search tool"; says not to use it to search symbols → `find_symbol` |

Total: **7 tools** (within the 6–8 limit). `init` is not a separate MCP tool — the server runs `reindex(force=false)` automatically at startup; `mct-cli` exposes `init` as a discoverability subcommand (equivalent to `reindex`).

No new tools (`find_types`, `find_tests`, `find_dead_code`, `semantic_search`) were added in this session; they remain out of scope under the explicit instruction. Before adding any in the future, check whether it can be an argument to an existing tool (for example, `find_symbol(name, kind)`) instead of a new tool.

**The `limit` parameter was added in a later session** to the five query tools with potentially unbounded results (`find_symbol`, `find_references`, `find_calls`, `find_callers`, `impact_analysis`). An audit found a real gap: none could bound its response, so a symbol with hundreds of hits in a large repository could produce more output than the `grep` this project is meant to replace. The parameter is `Option<usize>`, defaults to `50` (`mct-mcp-server/src/server.rs::DEFAULT_RESULT_LIMIT`, documented in place), and `format.rs` explicitly reports how many results were omitted when truncating. Verified with a new synthetic fixture, `mct-mcp-server/tests/fixtures/many-callers/` (one `target()` function + 70 `caller_NNN()` functions, deliberately exceeding the default), and three new tests in `tools.rs` covering default truncation, no truncation with a higher explicit `limit`, and independent per-section truncation in `impact_analysis`.

Verified: eight integration tests in `mct-mcp-server/tests/tools.rs` cover the seven tools (five original + three new truncation tests, including `impact_analysis` with deduplication of affected tests).
