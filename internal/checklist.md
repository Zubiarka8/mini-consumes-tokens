Los dos patrones de secretos reales de PHP siguen sin implementar.
3. **`find_implementations` sobre Go diferido a resolución de tipos vía LSP** — la implementación de interfaces en Go es estructural (el conjunto de métodos, no una palabra clave `implements`), determinada por el compilador; un heurístico de matching por AST no sería confiable. `mct-lang-go` solo expone relaciones explícitas de llamada/import; el símbolo de la interfaz y sus métodos declarados sí se indexan (ver fila de Go). Revisar junto con la decisión general de LSP (#1).
4. **`mct-lang-html` no reconoce motores de plantillas embebidos en `.html`** (Django Template Language, Jinja2, y cualquier otro que reutilice la extensión `.html`) — **verificado empíricamente esta sesión** con una plantilla Django realista (`{% extends %}`, `{% for %}`, `{{ variable }}`, `{% url %}`, `{% include %}`) a través de un test desechable ejecutado y borrado tras usarlo (mismo patrón que otros probes de esta sesión). Resultado real: `tree-sitter-html` **no reporta error de sintaxis** (es muy tolerante, trata `{% %}`/`{{ }}` como texto plano fuera de etiqueta), así que el archivo se indexa "sin problema" según `get_indexing_status` — pero produce símbolos/relaciones basura en las zonas con sintaxis de plantilla: un atributo `id="item-{{ item.id }}"` se indexó literalmente con las llaves incluidas en el nombre del `Element`; un atributo `class="{% if user.is_authenticated %}active{% endif %}"` se partió por espacios en 6 relaciones `References` sin sentido (`.{%`, `.if`, `.user.is_authenticated`, `.%}active{%`, `.endif`, `.%}`). Al mismo tiempo, todo lo semánticamente importante de Django desaparece sin avisar: `{% extends "base.html" %}`/`{% include "partials/footer.html" %}` no generan ninguna relación `Imports` (a diferencia de un `<link>`/`<script src>` real), y `{% block %}`/`{% for %}` no producen ningún símbolo — son simplemente texto no reconocido. El HTML real fuera de los template tags (etiquetas, `id`/`class` genuinos, `<link>`/`<script>`) sigue indexándose correctamente; el problema es localizado a las zonas con sintaxis de plantilla. **Pendiente de decisión del usuario, dos opciones planteadas, sin respuesta aún**: (a) documentar como limitación conocida en MANUAL §12 sin cambiar comportamiento, o (b) implementar algún tratamiento real (detectar sintaxis de plantilla y excluir/advertir sobre esos archivos, o un crate/heurística dedicada). No se ha tocado ningún archivo de código para esto — solo detección y reporte.

## Diseño de tools MCP

Criterio aplicado esta sesión: máximo 6-8 tools, cada una clasificada en Atómica / Compuesta / Administración del índice, con descripción anti-ambigüedad ("cuándo NO usar esta, usar Y en su lugar") cuando existe una tool parecida.

| Tool | Categoría | Ambigüedad resuelta contra |
|---|---|---|
| `find_symbol(name)` | Atómica | aclara no usarla para callers/referencias → apunta a `find_callers`/`find_references` |
| `find_references(symbol)` | Atómica | aclara no usarla si solo se quieren callers directos → apunta a `find_calls` |
| `find_calls(function)` | Atómica | aclara que es la inversa de `find_callers` |
| `find_callers(function)` | Atómica | aclara que es la inversa de `find_calls`; aclara no usarla para búsqueda amplia de referencias → apunta a `find_references`; aclara no usarla si se quiere blast-radius completo → apunta a `impact_analysis` |
| `impact_analysis(symbol)` | **Compuesta** (implementada esta sesión) | internamente combina `find_callers` + `find_references` + heurística de nombre de test (`test`/`test_*`), composición en Rust (`mct-mcp-server/src/server.rs::impact_analysis`), no delegada al agente. Aclara no usarla para lookup simple → más barato con `find_callers`/`find_references` solos |
| `reindex(force)` | Administración del índice | descripción marcada explícitamente "INDEX ADMINISTRATION, not a search tool" |
| `get_indexing_status()` | Administración del índice | descripción marcada explícitamente "INDEX ADMINISTRATION, not a search tool"; aclara no usarla para buscar símbolos → `find_symbol` |

Total: **7 tools** (dentro del límite de 6-8). `init` no es una tool MCP separada — el servidor corre `reindex(force=false)` automáticamente al arrancar; `mct-cli` sí expone `init` como subcomando de descubribilidad (equivalente a `reindex`).

Ninguna tool nueva (`find_types`, `find_tests`, `find_dead_code`, `semantic_search`) fue agregada esta sesión — quedan fuera de alcance según la instrucción explícita. Antes de agregarlas en el futuro: revisar si caben como parámetro de una tool existente (ej. `find_symbol(name, kind)`) en vez de una tool nueva.

**Parámetro `limit` agregado en sesión posterior** a las 5 tools de consulta con resultados potencialmente ilimitados (`find_symbol`, `find_references`, `find_calls`, `find_callers`, `impact_analysis`) — gap real detectado por auditoría: ninguna tenía forma de acotar la respuesta, así que un símbolo con cientos de hits en un repo grande podía emitir una respuesta más grande que el propio `grep` que el proyecto existe para reemplazar. `Option<usize>`, default `50` (`mct-mcp-server/src/server.rs::DEFAULT_RESULT_LIMIT`, documentado in situ), `format.rs` avisa explícitamente cuántos resultados se omitieron cuando trunca. Verificado con fixture sintético nuevo `mct-mcp-server/tests/fixtures/many-callers/` (1 función `target()` + 70 `caller_NNN()`, supera el default a propósito) y 3 tests nuevos en `tools.rs` confirmando truncamiento por default, no-truncamiento con `limit` explícito más alto, y truncamiento independiente por sección en `impact_analysis`.

Verificado: 8 tests de integración en `mct-mcp-server/tests/tools.rs` cubren las 7 tools (5 originales + 3 nuevos de truncamiento, incluyendo `impact_analysis` con deduplicación de tests afectados).
